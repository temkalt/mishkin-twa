## 2. Деплой: зафиксирован Vercel + управляемая Postgres

Раньше в репозитории жили два несовместимых сценария. Решение: **Vercel** —
фронт и бэк двумя проектами из GitHub, база — управляемая Postgres
(Neon/Supabase). Docker остаётся в репозитории как вариант для self-hosted VPS
(compose приведён в рабочий вид: Postgres-сервис, `migrate deploy`, запуск
собранного `node dist/index.js`), но локально не проверялся — Docker на машине
разработчика не запускается.

Чек-лист настройки — в [README](./README.md#деплой-на-vercel). Ключевое:

- `DATABASE_URL` и `DIRECT_URL` должны быть доступны **и на сборке** — миграции
  применяет `vercel-build` (`server/scripts/vercel-build.mjs`).
- Адрес бэкенда прописывается в двух местах: `vercel.json` фронта (rewrite
  `/api/*`) и `PUBLIC_URL` бэкенда (return_url оплаты).
- Вебхук бота ставится один раз через `/api/setup-webhook?secret=…`.
- URL уведомлений ЮKassa: `https://<бэкенд>/api/payments/webhook`.

Что помнить про serverless:

- `express-rate-limit` держит счётчики в памяти инстанса — при масштабировании
  лимит размывается. Для жёстких лимитов понадобится общий стор (Upstash/Redis).
- Рассылка идёт батчами по 25 с паузами: на больших базах упрётся в лимит
  времени функции. Тогда — очередь или крон.
- Prisma использует один клиент на инстанс (`lib/prisma.ts`); для пулера базы
  строка подключения должна быть pooled, а `DIRECT_URL` — прямой.

## 3. Сделано сверх блокеров (спринты 1–3)

- **Оплата ЮKassa:** создание платежа, страница подтверждения, вебхук с двойной
  проверкой (IP + перезапрос статуса через API), идемпотентность через
  `PaymentEvent`, опрос статуса из приложения, возвраты (`refund.succeeded`).
  Плюс встроенный **эмулятор** — сквозной поток отлаживается без реквизитов.
- **Форма оплаты внутри Mini App:** `embedded`-платёж, виджет ЮKassa рисуется на
  странице заказа, Telegram пользователь не покидает. Если виджет не поднялся —
  автоматический откат на страницу оплаты ЮKassa, заказ не зависает. Осталось
  проверить путь на тестовом магазине (`test_…`): эмулятор его не покрывает,
  он всегда отдаёт ссылку.
- **Учёт остатков** (`Product.stock`, миграция `20260818021500_product_stock`):
  списание в транзакции создания заказа условным `UPDATE … WHERE stock >= qty`
  (двойная продажа последней свечи невозможна), возврат на склад при отмене
  заказа ровно один раз (`Order.stockReturnedAt`), «осталось N шт.» в каталоге и
  карточке, потолок количества в корзине и блокировка чекаута с недоступным
  товаром, поле остатка в админке. `stock = null` — учёт по товару не ведётся,
  поэтому включение склада не ломает уже созданные товары.
- **Доставка:** единый справочник на сервере (`lib/delivery.ts`), цена доставки
  в заказе, порог бесплатной доставки, адрес обязателен только там, где нужен
  (самовывоз — без адреса), трек-номер и уведомление клиенту при смене статуса.
- **Валидация Zod** на всех записывающих роутах; цены пересчитываются на сервере
  из БД, клиент не может назначить свою.
- **HTTP-обвязка:** helmet, compression, `json({ limit: '100kb' })`,
  rate-limit на заказы/промокоды/пользователей, health-check с проверкой БД,
  наружу не утекают внутренние сообщения об ошибках.
- **Фронт:** чекаут отдельной страницей с маской телефона и согласием на
  обработку ПДн (вся строка согласия — одна кнопка-чекбокс: раньше галочка
  ставилась только точным попаданием по квадратику 20×20, а нажатие на текст
  уводило в документы), страница результата оплаты, юридические документы
  (`Legal`), галерея фото на карточке товара, состояния ошибок с «Повторить»,
  иконки inline-SVG (lucide) вместо шрифта Material Symbols, светлая тема
  зафиксирована, цвета шапки/фона Telegram выставляются под бренд.
- **Админка** синхронизирована с бэкендом: видит скрытые товары, статус и способ
  оплаты, суммы по позициям/доставке, принимает трек-номер, несколько фото у
  товара, остаток на складе.
- **CI** (`.github/workflows/ci.yml`): линт и сборка фронта, сборка бэка, прогон
  миграций на чистой Postgres + проверка отсутствия дрейфа схемы.
- **Сквозной тест** (`npm run test:e2e`, 29 проверок): валидация заказа, расчёт
  сумм и промокода, оплата эмулятором с повторным уведомлением, права доступа,
  склад — нехватка, списание, обнуление, возврат при отмене.

## 4. Что осталось

### P1 — до боевого запуска

1. **Загрузка изображений.** Админка принимает только ссылки. Нужен аплоад
   (Vercel Blob / S3 / Supabase Storage) с ресайзом — заказчик не будет
   выкладывать файлы руками.
2. **Наблюдаемость.** `pino` вместо `console.*`, Sentry на фронт и бэк, алерты на
   ошибки платежей и падение вебхука. Сейчас про сбой оплаты мы узнаем от клиента.
3. **Тесты на деньги.** Расчёт суммы, скидки и доставки, применение промокода,
   обработка уведомления ЮKassa (включая повтор того же события) — Vitest +
   supertest на тестовой базе. Сквозной сценарий уже покрыт `test:e2e`, но это
   один прогон целиком, а не быстрые модульные тесты на арифметику.
4. **Прогон на боевых реквизитах ЮKassa** после появления ИП: тестовый платёж,
   проверка чека и возврата. Отдельно — виджет: на тестовом магазине (`test_…`)
   пройти оплату картой внутри Mini App и убедиться, что 3-D Secure и СБП
   отрабатывают в webview Telegram; если нет — переключить фронт на
   `{ mode: 'redirect' }` (одна строка в `OrderResult.tsx`).
5. **Автоотмена зависших онлайн-заказов.** Неоплаченный заказ держит остаток до
   отмены руками. Нужен крон (или проверка при чтении), который через N часов
   отменяет `PENDING`/`UNPAID` и отпускает склад.

### P2 — сразу после запуска

- Пагинация товаров (`take/skip` уже есть у заказов) и серверный поиск —
  сейчас фильтрация по загруженному списку на клиенте.
- Промокоды: срок действия, минимальная сумма, «один на пользователя».
- Аналитика в админке: выручка по дням, конверсия, топ-товары; события
  «открыл товар / положил в корзину / оформил».
- Убрать неиспользуемое поле `User.isAdmin` — источник прав один, `ADMIN_IDS`.
- Характеристики товара отдельными полями (время горения, вес, воск) вместо
  описания. Пирамида аромата сознательно убрана с карточки — если вернём,
  данные уже есть (`topNote/heartNote/baseNote`).

### P3 — качество и скорость

- Self-hosted шрифты (`woff2` в `public/fonts`): сейчас Manrope и Jost тянутся с
  Google Fonts — лишняя внешняя зависимость для российских сетей.
- Vite manual chunks + анализ бандла; WebP/`srcset` для картинок; кэш товаров в
  сторе с TTL; prefetch страницы товара.
- Доступность: пройти по контрасту и фокус-стилям, `aria-label` там, где ещё нет.
- 152-ФЗ: если бэкенд и база уедут за пределы РФ — решить вопрос с хранением ПДн
  россиян (см. открытые вопросы).

## 6. Открытые вопросы к владельцу

1. **Свечи — собственное производство заказчика или перепродажа?** От этого
   зависит, законно ли принимать оплату через самозанятого (при перепродаже —
   нет) и на кого оформлять боевой аккаунт ЮKassa.
2. **Когда у заказчика появится ИП?** До этого живём на эмуляторе/sandbox.
3. **Нужна ли веб-версия магазина вне Telegram?** Telegram в РФ сильно
   ограничен, часть покупателей не откроет Mini App без VPN. Код к этому близок:
   при `ALLOW_BROWSER_DEMO=true` магазин уже работает в браузере — но тогда нужна
   своя авторизация вместо initData.
4. **Где хранить персональные данные?** 152-ФЗ требует хранения ПДн россиян в
   РФ. Vercel и Neon/Supabase — не РФ. Варианты: принять риск, либо база с ПДн в
   российском облаке, либо российский хостинг целиком.
